# 飞盘规则助手 · 产品准则

> 本文定义产品身份、目的和需求判断口径。ADR、README、提示词与界面文案
> 都应与本文一致。历史报告只记录当时的判断，不覆盖本文；
> 实现或线上状态以代码和实测为证据。

> 2026-10-23 由项目维护者定稿，作为当前产品准则。
> 它替代 2026-10-20 更狭窄的"唯一目的"表述。

## 产品定义

飞盘 RAG 系统是**面向飞盘运动的智能规则问答工具**。盘友可以用自己的话提出规则疑问
或描述比赛情境；系统依据可核对的规则资料，给出清楚、贴近问题的回答，并在需要时
展示相应依据。复盘是它支持的重要使用场景。

## 产品目的

**降低飞盘规则的查询与理解门槛。** 盘友遇到问题时，无须自行翻阅英文原文、中文译文
或规则 PDF，也能方便、可靠地弄明白相关规则。产品应好用到让盘友愿意在下次有疑问时
继续使用。

这里的“无须自行翻 PDF”指盘友**不必自己完成检索、翻译和比对工作**，不意味着隐藏官方
原文。可核查来源、引用不篡改、依据不足时承认不确定，仍是产品可信的基础。

## 希望产生的影响

更容易理解规则的盘友，可能更有把握地在比赛中运用规则、与队友或对手沟通并处理争议。
这是**长期观察的影响**，不能承诺每个人都会遵守规则，也不应作为筛选每项功能的唯一判据。

## 判断口径（先问这一句）

> **盘友带着真实规则疑问来，能否轻松问进去、看懂回答、核对依据，并愿意下次再用？**

对场景型功能，再问：它是否让盘友更容易回看、理解和解释那次经历？

- 准确率、检索命中、延迟是**保障指标**，不是产品目的本身；
- “30 位盘友说懂了”是早期用户验证；“约七成玩家喜欢”是长期目标，两者都要说明样本和口径；
- 不把“下一场少犯一次规”设为每项开发工作的唯一通过条件；
- 不承诺“让所有人遵守规则”——软件控制不了每个人的行为，只能降低理解门槛、提供可核对依据。

## 代表性情境（不是产品定义）

> **帮一个刚在飞盘上吃了亏、心里不服气的人，把事弄明白。**

它是**入口视角**，不是全部判据，也不是一票否决：
能帮这个人弄明白 → 优先考虑；不能直接帮这个具体场景的 → **不自动否定**，
它可能仍是同一产品的其他场景（查规则/练习/笔记/对话/复盘）。
是否做，按上面的判断口径 + 非目标/证据边界综合判断。

## 用户与场景

| 用户 | 他此刻的处境 | 他要的 |
|---|---|---|
| 零基础新手 | 连术语都没听过 | 把术语讲成人话 + 场上怎么办 |
| 玩过几次 | 不知道自己那次算不算 | 具体场景的答案 + 依据可核 |
| 老队员 | 记不清条号/数字 | 快速定位条款号和数字 |
| 队长/组织者 | 要转述、要定场地阵容 | 精确条款 + 尺寸/比例 |

**重要场景**：赛后复盘、赛前/训练学习、场下查规则与聊天。
复盘是重要场景，但不是唯一正统入口；首页进复盘还是对话，属于具体入口设计，
应看用户行为证据，不由一句原则替所有用户预先决定。

## 非目标（明确不做）

- 不做场上即时工具（手机不会掏出来）
- 不做社交/评论/排行榜/游戏化（当前非目标；不等于永久禁止任何账号/同步机制，
  但“可选同步/账号”必须另行论证并保护“打开即用、不收集身份”）
- 不做通用助手（豆包更会聊天；我们只守规则）
- 不做赛事报名/直播（葡萄飞盘的护城河，正面撞是死路）
- 不做广告；标准一旦卖了，就没人信

## 成功指标

- **早期**：30 个真实飞盘玩家，用真实问题验证能否轻松提问、看懂答案、核对依据、愿意再用；
  “懂了”是重要信号，不是唯一判据（样本、场景、口径要写清）
- **长期**：约七成飞盘玩家愿意使用并喜欢（总体、样本、指标、时间窗口待定义，
  不能用 DAU/查询量/测试通过率代替）
- **质量保障**：本仓库提供 297 条单测（`tests/`）与 5 个固定验收用例
  （`data/sample_questions.jsonl` + `scripts/verify_cases.py`）。
  生产版本另有基于 golden set 的质量闸门，未随本仓库发布。
- **长期价值**：有规则疑问时，盘友愿意再次打开并能借此弄明白；争议复盘的改善是可观察影响，
  不把“解决了多少次争议”作为唯一北极星。长期指标的测量口径仍待维护者确认。

## 产品准则与现状的边界

- 本文回答“为什么做、为谁做、怎样判断值得做”，不宣称当前代码已经全部做到。
- 当前对话、复盘、查规则、练习、笔记是不同入口；**核心任务始终是自然语言规则问答**。
- 首页默认进对话还是复盘属于入口设计：旧 ADR 仍记录复盘优先，当前代码与测试的落点是对话，
  **不得把任一方写成已定原则**。
- 产品自主语言使用飞盘语境；规则原文、`citations`、直接引文及用户原话保持原样。
- 旧报告、ADR 和评测数值保留为历史证据；与本文冲突时，先按本文理解产品目标，
  再以代码和只读实测核对实现状态，并显式记录冲突。

## 设计原则

1. **第一屏要说明这是什么**：一句标题 + 一句依据说明 + 少量示例；
   示例点了只填入输入框、不直接发送。不要问候、不要“猜你想问”。
   （2026-10-22 看过预览后决定恢复介绍——空白首屏不可接受。）
2. **惊喜由用户触发**：场不是一进来就铺开，是点了「摆到场上」才展开。
3. **零编造**：条款里没有的，就说“规则没写”；不补、不猜、不装懂。
4. **克制**：一屏一个主动作；宁可少一个功能，不要多一个半成品。
5. **语言分层**：产品自主表达用飞盘语境；官方原文、引用、用户原话逐字保留。
6. **不替用户裁决**：讲清认定标准、给可核对依据和沟通路径，不代替双方做现场判罚。
